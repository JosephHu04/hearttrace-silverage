# 全流程与数据库审查（2026-09-16）

## 结论与范围

当前具备“新家属申请 → 管理员审核并绑定已有老人 → 已有老人授权聊天 → 分析任务 → 人工复核 → 家属查看摘要并跟进 → 审计与撤销授权”的后端闭环；本轮新增的贯穿测试已通过。

尚不具备“全新老人和家属从零开户，到全部功能可用”的完整产品闭环。老人端仍自动使用预置演示身份；创建老人账号、真实登录、首次绑定、量表答题计分、实际视频通话与硬件管理没有完成。现阶段应称为三端集成原型，而非已完成上线验收的系统。

审查对象是 `chore/three-client-integration` 分支和本地 8010 API 所使用的 `.local/hearttrace-integration.db`。测试使用合成账号。模型分析在自动测试中使用确定性的替身，不代表真实模型准确性或外部服务已验证可用。本轮未进行真实用户资料导入或真实模型评测。

## 优先修复的剩余问题

### P0：完整试用前必须补齐

1. **老人身份入口缺失。** 增加由管理端核验创建老人账号、账号激活或安全配对、老人端登录/退出以及家属绑定核验。验收时必须使用新创建的老人，不能依赖 `elder-demo-001`。
2. **分析运行缺乏托管。** 统一 API 与两个 Worker 的数据库配置，增加统一启动、任务积压/失败可见性、重试入口和进程重启。验收以一次明确授权的合成聊天在真实配置下产生分析、复核并发布为准。
3. **新用户和日常正常状态的摘要不完整。** `family_today` 无摘要时返回 404，且按最新记录取值、不限定今天；`daily_care` 分析仅保存分析，不进入发布摘要路径。应区分“未产生摘要”“等待分析”“等待复核”“历史摘要”和“今日摘要”，并为正常日常状态明确发布策略。
4. **关怀指数不是标准化心理测评分。** `publish_confirmed_analysis_summary` 使用等级到 82/72/60/45 的固定映射，基线变化也是固定值；前端却显示“较个人近 7 天基线”。应先移除或明确标注演示分数，再完成有版本的量表、逐题答案、确定性服务端计分和真实时间窗口基线。不能把当前数值作为测评准确性的证据。
5. **新增分析与人工审核的并发一致性。** 同会话追加候选时会更新风险事件的 `source_analysis_id`，但没有同步提高 `version`；新的紧急候选合并到已有普通事件时，也没有更新其优先级与处理时限。需要带版本比较的原子更新，避免审核人员用旧证据确认新摘要或漏掉加急候选。
6. **授权撤回还缺完整入口与证据。** 分析 Worker 调用前检查布尔授权，但没有面向老人的撤回接口和完整授权历史。家属申请中的 `consentVersion` 与管理员批准不能替代老人授权证据；需明确记录老人确认、用途、时间及撤回，并处理排队和正在执行的任务。

### P1：发布前的数据库与运行保障

- 审批需原子地判断“仍待审核”并更新，注册唯一键冲突需稳定返回业务错误；当前先查询后写入的路径仍需并发验证。
- 增加合理的数据库 CHECK 约束（状态、年龄、数值范围）、关系角色校验及必要索引。现有外键主要验证记录存在，不验证关联账号角色。
- 生产初始化统一走迁移，避免依赖应用启动时 `create_all`；增加 PostgreSQL CI 和多 Worker 并发、崩溃后租约恢复测试。
- 当前 Worker 的第三次领取后若进程崩溃，任务可能保持 `processing` 且因达到尝试上限无法再次领取；需要超时终结和人工重放路径。
- 聊天原文、账号标识与注册申请有保留策略需求：定义期限、删除/匿名化路径、备份保留和访问控制。密码已有哈希存储，但不等于整库健康资料已加密。
- 增加登录/注册限流、正式管理账号初始化、长连接认证复核，以及能区分数据库和 Worker 状态的就绪检查。
- 备份副本通过完整性检查只是本次演练；仍需定时备份、异机保存、失败告警和周期恢复演练。
