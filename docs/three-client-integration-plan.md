# 三端整合执行清单

本清单规定老人端、家属端、管理端在比赛开发期如何共同接入同一套业务后端。它以合成演示数据为前提，不可用于真实医疗诊断或真实紧急服务。

## 1. 唯一事实来源

正式联调和部署环境采用一套核心 API 与一套 PostgreSQL 业务数据库。三个前端不得直接连接数据库，也不得各自保存风险状态、家属授权或老人身份副本。

```text
老人端 / 家属端 / 管理端 / 后续设备
                    ↓
                 核心 API
                    ↓
        PostgreSQL + Outbox + Worker
```

本地开发可使用每人独立的 SQLite 或 PostgreSQL 数据库，避免开发数据互相污染；合成跨端联调、比赛演示和测试环境必须使用同一份数据库。

所有跨端关联都使用稳定的 `elderId`，不得依据老人姓名、手机号或页面显示名称关联。

## 2. 统一启动约定

| 服务 | 默认端口 | 用途 |
| --- | --- | --- |
| 核心 API | 8000 | 认证、授权、会话、风险、通知和审计 |
| 家属端 | 3000 | 经授权的关怀摘要与行动 |
| 管理端 | 3001 | 人工复核、授权、紧急事件与审计 |
| 老人端 | 3002 | 陪伴、授权、筛查与求助 |

三个前端的 `NEXT_PUBLIC_API_BASE_URL` 统一填 API 的**域名与端口**，例如 `http://127.0.0.1:8000`，**不要附加 `/api`**。前端代码自己拼接 API 路径；原先老人端的 `/api` 配置仍兼容，但新配置一律用同一种格式。否则家属端和管理端会误请求 `/api/api/...`。CORS 仅放行当前测试环境中的三个前端域名。模型密钥、数据库密码、真实联系方式和真实健康数据均不得提交到 Git。

## 3. 合并规则

1. `main` 是唯一集成基线，禁止直接推送。
2. 每位成员从最新 `origin/main` 建立功能分支，不从本机的旧副本继续叠加功能。
3. 涉及数据库、接口、授权或风险流程的改动，先更新 `docs/api-contract.md`，再提交后端迁移和客户端实现。
4. 每个 Pull Request 只解决一个主题；共享文件由公共后端负责人优先合并，三端随后更新调用。
5. 不通过文件管理器复制或覆盖 `apps/elder`、`apps/family`、`apps/admin`。本机独立副本仅作界面参考或隔离开发。

建议分支：

- `feature/core-screening-device-contract`：公共接口、迁移、权限与 Worker。
- `feature/elder-consent-screening-safety`：老人授权、打卡、量表、呼救和视频请求。
- `feature/family-screening-video-status`：家属筛查摘要、视频状态和通知跳转。
- `feature/admin-screening-device-review`：筛查、跌倒和视频请求的人工复核。
- `chore/three-client-integration`：放联调文档、环境约定、跨端回归测试和联调中必须一起修正的质量问题；后续新业务功能仍分端开 PR。

## 4. 首个必须跑通的闭环

```text
老人明确同意保存与健康关怀分析
  → 核心 API 保存会话并写入引用型 Outbox
  → 分析 Worker 产生结构化候选信号
  → 管理端人工复核
  → 发布不含原文的每日关怀摘要
  → 通知有授权的家属
  → 家属记录已联系、视频安排或转介申请
```

家属端和管理端不得读取聊天全文。模型不能诊断、不能直接定级风险、不能直接创建紧急事件或直接向家属发布结论。

## 5. 近期接口工作

已具备的公共能力包括账号审批、家属授权、聊天会话、风险复核、紧急求助、审计和站内通知。

以下能力必须由公共后端先落地，再由三端并行接入：

| 能力 | 后端责任 | 老人端 | 家属端 | 管理端 |
| --- | --- | --- | --- | --- |
| 每日打卡 | 保存自述、趋势与授权 | 心情、睡眠、社交意愿 | 查看趋势 | 查看异常变化 |
| 标准筛查 | 模板版本、服务端计分、结果区间 | 自愿答题 | 仅看完成状态与建议 | 复核与转介 |
| 视频联络 | 请求、状态、已绑定联系人 | 发起/取消请求 | 接受、改约、记录安排 | 必要时协调 |
| 设备与跌倒 | 设备绑定、签名、遥测、候选事件 | 显示设备状态 | 只看必要事件状态 | 判定确认或误报 |

危机语言、PHQ-9 第九题非零、确认跌倒和一键呼救必须进入独立安全流程，不与普通情绪趋势合并计算。

## 6. 验收顺序

1. 数据库迁移可从空库升级到最新版本，`alembic check` 无差异。
2. 三端能登录并读取同一个 `elderId` 的合成数据。
3. 老人紧急求助后，管理端和授权家属均收到通知；未授权家属无法读取事件或老人数据。
4. 管理端确认与解除事件后，家属端安全状态同步更新；每一步均留审计记录。
5. 授权聊天分析经人工确认后，家属端只看到结构化摘要，不看到原文。
6. 家属注册通过、授权修改和撤销立即影响接口权限，不以重新登录为前提。

## 7. 当前本地联调结果

在 `chore/three-client-integration` 工作区中，Python 3.11 数据库迁移、50 项 API 测试、三端 ESLint 与生产构建、三端前端依赖安全审计和“老人求助 → 管理端处置 → 授权家属通知 → 未授权隔离”真实 HTTP 烟雾测试均已通过。浏览器中已核对老人端授权/呼救确认与家属登录前拦截，并修正了管理端的联调地址错配。该结果只使用独立 SQLite 合成数据库；下一阶段切换到共享 PostgreSQL 测试库。
