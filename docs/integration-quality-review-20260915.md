# 三端整合质量复核（2026-09-15）

本轮只使用合成老人、家属和工作人员账号及独立 SQLite 数据库。它是比赛演示前的稳定性复核，不等同于医疗、紧急服务或真实用户验收。

## 对照与取舍

- Seva AI 的开源老人陪伴实现把每日问候、家属仪表盘、提醒与会话历史放在同一流程中。本项目优先保留人工复核和授权隔离，不把聊天全文作为家属端默认功能。
- SilverMind 的公开架构强调一个共享数据事实来源、隐私优先与失败时关闭访问。本项目三端统一接核心 API；家属端移除离线 Mock 回退，避免把演示数据误认为真实老人状态。
- OpenEMR 的权限文档将访问范围和撤销作为独立能力；Medplum 的集成文档强调审计事件。本项目已对摘要查看、授权变更、关怀行动、紧急处置留痕，但真实生产仍需要更严格的会话和操作审计。

## 已闭环的问题

| 问题 | 处理 | 回归依据 |
| --- | --- | --- |
| 老人端动态时间导致首屏水合不一致 | 首次渲染保持稳定占位，挂载后更新时间 | 浏览器刷新无新错误；生产构建通过 |
| 家属端网络失败仍可能使用 Mock 或过期摘要 | 删除无认证的 Mock API 与假数据回退；401 清理会话 | 家属端首屏先进入登录；构建/类型检查通过 |
| 家属注册状态查询泄露申请人联系方式等字段 | 公共查询只返回审核状态与时间 | API 回归测试 |
| 修改密码后旧 JWT 在有效期内仍可使用 | 令牌签发时间与密码变更时间比较；旧令牌 401 | API 回归测试 |
| 忘记密码伪报“已发送”但无发送器 | 公共请求统一 503，前端明示暂未开通 | 已注册/未注册标识符响应相同 |
| 演示登录和默认 JWT 秘钥可能进入生产 | 生产启动守卫，演示登录可单独关闭 | API 安全基线测试 |
| 老人端没有把现有呼救接口接到触屏 | 增加大按钮、二次确认、状态反馈和失败时直接求助提示 | 浏览器核对确认框；真实 HTTP 跨端烟雾测试 |
| 老人端默认不保存也不分析，家属关怀摘要无法由新聊天更新 | 老人先自行选择私密会话或授权关怀摘要 | 浏览器核对两种明确选择 |
| 三端 API 地址格式不一致导致 `/api/api/...` | 统一配置为 API origin，老人端兼容旧 `/api` 后缀 | 管理端从 Not Found 恢复为真实 API 连接 |
| 边看本地预览边跑生产构建覆盖 `.next` 缓存 | 开发和生产构建使用独立输出目录 | 同时预览与构建不再争用同一缓存 |
| 家属端 `next lint` 无法运行、老人/管理端缺静态检查 | 三端 ESLint 命令和 CI 检查 | 三端 lint、生产构建均通过 |
| 三端传递依赖 PostCSS 的安全告警 | 固定安全版本并更新锁文件 | npm/pnpm 审计为 0 已知漏洞 |
| 管理端 CI 锁定的 pnpm 版本不识别构建脚本白名单 | 统一为支持 `allowBuilds` 的 pnpm 10.26 | 锁文件安装与构建校验 |
| 管理端直接自动演示登录，正式环境关闭演示入口后无法打开 | 改为独立管理员密码登录；后端管理员权限通过后才显示工作台；退出/令牌失效清会话 | 管理端 lint/build、API 密码登录与家属角色隔离回归；本地登录页检查 |

## 本轮验证

- API：Python 3.11，最新 `pytest` 为 52 passed；数据库迁移与 `alembic check` 已在整合工作区验证。
- 三端：ESLint 与 `next build` 全部通过；家属、老人 npm 审计与管理 pnpm 审计为 0 已知漏洞。
- 真实 HTTP 闭环：老人求助、请求幂等、管理端收到和处置、授权家属通知与状态更新、无授权家属隔离、通知已读及审计记录全部通过。
- 浏览器：家属未登录时进入独立登录页；管理端接入真实共享 API；老人端刷新无新的水合/运行错误，并显示授权选择和呼救二次确认。

## 仍不能宣称完成的部分

1. 老人端仍使用**合成演示身份自动登录**。管理端已有账号密码登录，但正式管理员账号的安全创建、分配和密码找回仍未实现；生产启动已禁止演示登录与演示数据。两端不能直接部署给真实用户。
2. 忘记密码**尚未接邮件/短信发送渠道**，因此现在明确返回“暂未开通”，不会伪报成功或生成无法交付的令牌。上线前必须接入并测试发送、限流、滥用防护与失败重试。
3. 当前还没有真实的标准化筛查答题与服务端计分、视频联络状态机、语音与设备防跌倒数据闭环；现有趋势和风险演示数据不能代替临床验证。
4. 共享 PostgreSQL 测试库、真实跨浏览器端到端自动化、监控告警、备份恢复、负载与断网测试仍待完成。即使本轮无已知低级错误，也不能保证以后绝无故障。

下一轮建议先完成正式身份与找回密码，再做打卡/筛查/视频请求的公共契约，最后上设备与跌倒检测。新业务按端拆分 PR，公共数据结构先由核心 API 负责人合并。
